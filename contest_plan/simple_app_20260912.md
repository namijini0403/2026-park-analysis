# 학교 한 곳에서 시작하는 구조 — 2026-09-12

## 목적

교육자원의 존재보다 학생에게 닿을 조건을 확인하고, 담당자가 근거로 판단하도록 돕는다. DATA_ROCK 원본의 도달성·설명 가능성·담당자 승인 철학을 유지하되, 자동 우선안 하나를 강제하는 과거 설계는 2026-09-12 사용자 원칙에 따라 사용하지 않는다. 원본 HWP는 수정하지 않았다.

## 사용자 흐름

1. 학교급과 학교를 선택한다. 기본은 초등학교이며 가나다순이다.
2. 공원·도서관·장서·운동·돌봄 중 자원을 선택한다.
3. 확인된 사실, 더 확인할 조건, 검토할 방법을 읽는다.
4. 같은 화면의 챗봇에 질문한다. 관련 시설 자료와 근거 원문, 질문한 통계 결과를 확인하고 저장한다.

화면 상단의 여러 분석 탭·두 챗봇·후보지 시뮬레이션·복잡한 지도 레이어를 기본 흐름에서 제거했다. 자료 관리는 운영 담당자의 별도 링크로 유지한다. 첫 화면에서 학교를 임의로 선택하지 않는다. 기술 내용은 답변 근거의 펼침 영역에 둔다.

## 데이터와 RAG 경계

- 수치의 단일 원본: `data_processed/education/analysis_dataset.json` 및 `data_processed/student_services/priorities.json` 등 기존 승인 산출물.
- 학교 요약: 서버가 원장에서 학교 ID를 확인하고 필요한 관측만 선택한다. 클라이언트가 보내는 지표·Case·점수는 읽지 않는다.
- 설명 원본: `rag/policy-guide.md`, `rag/analysis-guide.md`. 주제별 설명과 방법·한계·원자료 경로를 분리해 관리한다.
- 세부 학교 근거: `api/_education_evidence.js`, `api/_context_evidence.js`의 서버 자료 조회를 재사용하되 과거 후보 가중합·Case 기본 권고 chunk는 제외한다.
- 계산: 질문의 변수와 학교급을 정한 뒤 기존 결정론적 계산을 사용한다. LLM이 수치나 코드를 생성하지 않는다. 일반 '관련 자료' 질문을 통계 요청으로 보내지 않는다.
- 통계 관계는 선택 학교의 학교급 전체(또는 질문한 지역)를 사용하고, 특정 학교 학생 수 추세는 그 학교만 사용한다. 답변에 범위를 명시한다.
- 생성: 최대 5개 근거, 각 본문 최대 7,000자, 기존 최대 출력 토큰 설정을 유지한다. AI 연결 실패 시 원문 근거를 표시한다. 대화 전체를 계속 전송하거나 문서를 중복 임베딩하지 않는다.
- 기록: 답변·원문·관측표·계산 조건·원자료 해시를 JSON으로 저장할 수 있다. 질문은 매번 선택 문맥을 명시하며 지난 답변의 학교 라벨은 유지한다.

문서 하나에 모든 수치를 복사하면 갱신 때 불일치가 생기므로 설명은 RAG, 현재 숫자는 원자료 조회로 나눴다. 현재 검색은 소규모 태그 기반 RAG이며 임베딩 검색, 업로드 문서의 자동 인덱싱, 대명사 기반 장기 대화 기억은 구현 범위가 아니다.

## 판단 제약

미수집·부분수집을 확정 부족으로 바꾸지 않는다. 이용·안전·실행·출입구 경로를 다른 장점으로 상쇄하지 않는다. 종합점수와 전체 학교 순위, 단일 자동 추천은 생성하지 않는다. 현재 검증되지 않은 후보에 순위를 요청하면 보류 이유를 답한다. 도서·농어촌 학교는 별도 검토한다. 낡은 localStorage 추천과 과거 정책 카드 우선안은 새 화면의 입력이 아니다.

## 보존과 실행

`park-railway-deploy`가 실제 수정 대상이다. 다른 복제 저장소에 변경을 중복 반영하지 않았다. 직전 메인 HTML은 `archive/20260912-before-simple/`에 보존했다. 데이터·수집 파이프라인·승인 센터·기존 작업 변경을 되돌리지 않았다. 기본 빌드에서 iframe/Vite 빌드를 제거했고, 분석 서버와 승인 자료는 유지한다.

`npm run build:vercel` 후 `npm start`. HTTP 정적 서버만으로는 새 API 기반 앱이 동작하지 않는다. 이번 작업은 로컬 코드와 빌드까지이며 운영 배포를 수행하지 않았다.
